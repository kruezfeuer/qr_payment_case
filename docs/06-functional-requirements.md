# Функциональные требования

## 1. Назначение документа

Документ определяет функциональные требования к сервису приёма платежей по QR-коду.

Требования декомпозируют бизнес-процесс и сценарии использования в проверяемое поведение системы.

## 2. Термины

| Термин | Определение |
|---|---|
| Платёжный запрос | Сущность, описывающая конкретную покупку и параметры предстоящей оплаты |
| QR-код | Код, позволяющий идентифицировать платёжный запрос |
| Платёжная операция | Попытка проведения платежа по платёжному запросу |
| Итоговый статус | Статус, подтверждающий завершение обработки операции |
| Идемпотентность | Свойство повторного выполнения одного запроса, предотвращающее дублирование бизнес-операции |

## 3. Приоритеты требований

| Приоритет | Значение |
|---|---|
| Обязательный | Требование необходимо для реализации основного сценария MVP |
| Желательный | Требование может быть реализовано после основных функций |

Все требования, перечисленные ниже, имеют приоритет «Обязательный», если явно не указано иное.

## 4. Создание платёжного запроса

| ID | Требование | Связанный сценарий |
|---|---|---|
| FR-001 | Сервис должен принимать запрос на создание платёжного запроса от зарегистрированной торговой точки, имеющей право принимать платежи. | UC-01 |
| FR-002 | Сервис должен проверять наличие обязательных параметров: идентификатора заказа, суммы и валюты платежа. | UC-01 |
| FR-003 | Сервис должен проверять корректность формата и допустимость значений входных параметров. | UC-01 |
| FR-004 | Сервис должен проверять, что сумма платежа положительна и соответствует установленным ограничениям. | UC-01 |
| FR-005 | При успешном создании сервис должен присваивать платёжному запросу уникальный идентификатор и определять срок его действия. | UC-01 |
| FR-006 | Сервис должен формировать динамический QR-код, связанный с конкретным платёжным запросом. | UC-01 |
| FR-007 | В ответ на успешное создание сервис должен возвращать идентификатор запроса, данные QR-кода и срок его действия. | UC-01 |
| FR-008 | Сервис должен поддерживать безопасную повторную обработку запросов создания платежа. Повтор с тем же ключом идемпотентности не должен создавать новый платёжный запрос. | UC-01 |

## 5. Получение информации о платеже

| ID | Требование | Связанный сценарий |
|---|---|---|
| FR-009 | Сервис должен предоставлять возможность получить информацию о платёжном запросе по идентификатору, извлечённому из QR-кода. | UC-02 |
| FR-010 | Перед передачей данных платежа сервис должен проверить существование запроса, его срок действия и возможность проведения оплаты. | UC-02 |
| FR-011 | При успешной проверке сервис должен возвращать сведения о получателе, сумме, валюте и назначении платежа, если оно задано. | UC-02 |
| FR-012 | Сервис не должен позволять начать новую оплату по запросу, который уже оплачен или срок действия которого истёк. | UC-02 |

## 6. Подтверждение и проведение платежа

| ID | Требование | Связанный сценарий |
|---|---|---|
| FR-013 | Сервис должен принимать команду подтверждения платежа от авторизованного клиента через банковское приложение. | UC-02 |
| FR-014 | Перед проведением платежа сервис должен повторно проверить актуальность запроса, отсутствие уже выполняющейся операции по нему и соблюдение установленных ограничений. | UC-02 |
| FR-015 | При начале проведения платежа сервис должен создавать отдельную платёжную операцию с уникальным идентификатором и связью с соответствующим платёжным запросом. | UC-02 |
| FR-016 | Сервис должен передавать данные платёжной операции во внешнюю платёжную инфраструктуру через согласованный интеграционный интерфейс. | UC-02 |
| FR-017 | Сервис должен обеспечивать идемпотентность команды подтверждения платежа, чтобы повторный запрос не приводил к дублированию одной операции. | UC-02 |
| FR-018 | Сервис должен сохранять полученные результаты проведения платежа и соответствующие изменения статуса операции. | UC-02 |
| FR-019 | Если окончательный результат не получен в установленное время, сервис должен сохранять неопределённый или промежуточный статус и предусматривать получение актуального результата. | UC-02 |
| FR-020 | После подтверждённого успешного проведения платежа сервис должен переводить платёжный запрос в состояние, исключающее повторную успешную оплату той же покупки. | UC-02 |

## 7. Получение и передача статуса

| ID | Требование | Связанный сценарий |
|---|---|---|
| FR-021 | Сервис должен предоставлять авторизованным участникам возможность получить актуальный статус платёжной операции в пределах их прав доступа. | UC-03 |
| FR-022 | Сервис должен передавать торговой точке итоговый статус платежа по согласованному механизму интеграции. | UC-04 |
| FR-023 | Сервис должен предусматривать повторную доставку уведомления о результате, если предыдущая попытка завершилась ошибкой. | UC-04 |
| FR-024 | Повторная доставка уведомления не должна приводить к повторному проведению платежа или повторному выполнению бизнес-действий. | UC-04 |

## 8. Обработка ошибок и аудит

| ID | Требование | Связанный сценарий |
|---|---|---|
| FR-025 | При отклонении запроса сервис должен возвращать структурированный ответ с кодом ошибки и информацией, достаточной для обработки ошибки вызывающей стороной. | UC-01, UC-02, UC-03 |
| FR-026 | Сервис должен проверять права доступа вызывающей стороны перед предоставлением сведений о платёжном запросе или операции. | UC-01, UC-02, UC-03 |
| FR-027 | Сервис должен сохранять историю значимых изменений статуса платёжного запроса и платёжной операции с указанием времени изменения. | UC-01, UC-02, UC-03, UC-04 |

## 9. Ограничения реализации

1. Сервис отвечает за платёжные запросы, платёжные операции и их состояния, но не за управление заказами торговой точки.
2. Итоговый статус успешного платежа должен основываться на подтверждённом результате платёжной инфраструктуры.
3. Механизм получения результата от внешней системы — синхронный ответ, callback, запрос статуса или их комбинация — определяется при проектировании API.
4. Просмотр истории платежей как отдельная пользовательская функция не входит в текущий MVP.
5. Возвраты, частичная оплата и разделение одной покупки на несколько платежей не входят в текущий MVP.
