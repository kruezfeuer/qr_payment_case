# Нефункциональные требования

## 1. Назначение документа

Документ определяет нефункциональные требования к сервису приёма платежей по QR-коду.

Требования устанавливают ожидаемые характеристики производительности, доступности, безопасности, целостности данных и наблюдаемости системы.

## 2. Производительность

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-001 | Сервис должен отвечать на запросы создания платёжного запроса, получения данных платежа и получения текущего статуса с временем ответа не более 1 секунды для 95% запросов. Время ожидания ответа внешней платёжной инфраструктуры не включается в этот показатель. | При нагрузочном тестировании 95-й перцентиль времени ответа указанных операций не превышает 1 секунды в согласованном профиле нагрузки. |
| NFR-002 | Сервис должен поддерживать согласованный ожидаемый объём запросов от торговых точек и банковских приложений без нарушения требований производительности. | Целевой профиль нагрузки и допустимый уровень ошибок утверждаются до нагрузочного тестирования. |

## 3. Доступность и надёжность

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-003 | Целевая доступность API сервиса должна составлять не менее 99,9% за календарный месяц, за исключением согласованных регламентных работ. Это предварительная цель проектного кейса. | Показатель рассчитывается по согласованной методике мониторинга доступности API сервиса. |
| NFR-004 | Сервис не должен подтверждать успешное создание платёжного запроса до сохранения необходимых данных. | После подтверждённого успешного ответа данные запроса доступны для последующего чтения. |
| NFR-005 | Временная недоступность внешней платёжной инфраструктуры не должна приводить к автоматическому созданию дублирующих операций. | При моделировании тайм-аута и повторной отправки подтверждения не создаются дублирующие платежи. |
| NFR-006 | Сервис должен обеспечивать возможность восстановления актуального статуса операции после временной потери связи с внешней платёжной инфраструктурой. | После восстановления связи статус операции может быть уточнён без повторного инициирования той же оплаты. |

## 4. Безопасность

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-007 | Взаимодействие сервиса с внешними системами должно выполняться по защищённым каналам связи в соответствии с согласованными стандартами информационной безопасности. | Интеграции используют утверждённый механизм защиты транспорта. |
| NFR-008 | Сервис должен проверять подлинность вызывающей стороны и её права на выполняемую операцию. | Запрос от неавторизованного участника или запрос без необходимых полномочий отклоняется. |
| NFR-009 | Доступ к данным платёжных запросов и операций должен ограничиваться ролью и контекстом вызывающей стороны. | Торговая точка не может получить сведения об операциях другой торговой точки без соответствующих полномочий. |
| NFR-010 | В журналах не должны сохраняться секреты авторизации, полные платёжные токены или иные данные, раскрытие которых не требуется для диагностики. | Проверка журналов не выявляет запрещённые к сохранению значения. |

## 5. Целостность данных и согласованность состояний

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-011 | Денежные суммы должны храниться и обрабатываться без потери точности. | Для денежных операций не используются вычисления с плавающей точкой, приводящие к ошибкам округления. |
| NFR-012 | Повторные запросы и конкурентные команды подтверждения должны обрабатываться так, чтобы одна покупка не оплачивалась успешно более одного раза. | Параллельная отправка нескольких запросов подтверждения не приводит к нескольким успешным платежам по одному платёжному запросу. |
| NFR-013 | Изменения статуса платёжной операции должны сохраняться согласованно с историей соответствующих событий. | При проверке операций журнал истории соответствует фактически сохранённым изменениям состояния. |
| NFR-014 | Сервис не должен переводить завершённую операцию в другое итоговое состояние только из-за повторного или запоздавшего уведомления. | Повторное уведомление с тем же событием не изменяет итоговый статус операции. |

## 6. Наблюдаемость и аудит

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-015 | Сервис должен поддерживать корреляцию запросов между собственными компонентами и внешними интеграциями. | По идентификатору корреляции можно найти связанные записи обработки запроса. |
| NFR-016 | Сервис должен регистрировать значимые бизнес-события: создание платёжного запроса, создание операции, изменение статуса и попытки доставки уведомлений. | Для указанного события доступны идентификатор объекта, время, тип события и результат обработки. |
| NFR-017 | Ошибки интеграций, задержки обработки и неуспешная доставка уведомлений должны быть доступны для мониторинга. | Контрольные сценарии с ошибками отражаются в согласованных метриках или журналах мониторинга. |

## 7. Работа со временем и форматами

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-018 | Время создания и изменения объектов должно сохраняться в едином согласованном формате. Для хранения используется UTC, для передачи времени в API — формат ISO 8601 с указанием часового пояса. | Значения времени можно однозначно интерпретировать и сопоставить между системами. |
| NFR-019 | Срок действия платёжного запроса должен проверяться относительно доверенного времени сервера, а не времени устройства клиента. | Изменение времени на устройстве клиента не позволяет использовать истёкший платёжный запрос. |

## 8. Совместимость и развитие

| ID | Требование | Критерий проверки |
|---|---|---|
| NFR-020 | Изменения API не должны нарушать работу согласованных предыдущих версий интерфейса без установленной процедуры вывода версии из эксплуатации. | Совместимость подтверждается проверками контрактов для поддерживаемых версий. |
| NFR-021 | Архитектура интеграций должна позволять изменять механизм получения результата платёжной операции без изменения внешнего бизнес-смысла статусов. | Изменение способа доставки результата не требует изменения семантики платёжного запроса и операции. |

## 9. Допущения и открытые вопросы

Следующие параметры пока являются предварительными и требуют подтверждения:

1. Целевая производительность API и профиль нагрузки.
2. Целевая доступность сервиса и методика её расчёта.
3. Сроки хранения истории операций и аудита.
4. Утверждённые стандарты информационной безопасности.
5. Требования к резервированию, восстановлению и допустимой потере данных.
6. Пиковая нагрузка в периоды массовых покупок.
7. Требования к времени реакции на недоступность внешней платёжной инфраструктуры.

Числовые значения и эксплуатационные ограничения должны согласовываться с владельцем продукта, архитектором и ответственными за эксплуатацию и безопасность до выхода системы в промышленную среду.
