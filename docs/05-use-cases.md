# Сценарии использования

## 1. Назначение документа

Документ описывает сценарии взаимодействия пользователей и внешних систем с сервисом оплаты по QR-коду.

Сценарии используются для детализации требований, проектирования API, разработки тестовых сценариев и определения критериев приёмки.

## 3. UC-01. Создать платёжный запрос и QR-код

### Основная информация

| Параметр | Описание |
|---|---|
| Идентификатор | UC-01 |
| Цель | Создать платёжный запрос для конкретной покупки и вернуть торговой точке QR-код |
| Основной актор | Система торговой точки |
| Система | Сервис оплаты по QR-коду |
| Предусловия | Торговая точка зарегистрирована и имеет право принимать платежи |
| Триггер | Покупка подготовлена к оплате |

### Входные данные

- Идентификатор торговой точки.
- Идентификатор заказа в системе торговой точки.
- Сумма покупки.
- Валюта.
- Описание покупки, если оно требуется.
- Дополнительные параметры срока действия, если они поддерживаются.

### Основной сценарий

1. Система торговой точки отправляет запрос на создание платёжного запроса.
2. Сервис проверяет обязательные поля и корректность формата входных данных.
3. Сервис проверяет регистрацию и доступность торговой точки.
4. Сервис проверяет допустимость суммы и валюты.
5. Сервис проверяет уникальность операции в контексте торговой точки.
6. Сервис создаёт платёжный запрос и присваивает ему уникальный идентификатор.
7. Сервис определяет срок действия запроса.
8. Сервис формирует динамический QR-код, связанный с созданным запросом.
9. Сервис возвращает торговой точке идентификатор запроса, данные QR-кода и срок его действия.

### Альтернативные сценарии

**A1. Некорректные входные данные**

1. Сервис обнаруживает отсутствие обязательного поля или неверный формат значения.
2. Сервис возвращает ошибку валидации.
3. Платёжный запрос не создаётся.

**A2. Недопустимая сумма**

1. Сервис проверяет сумму и обнаруживает нарушение ограничения.
2. Сервис возвращает ошибку с идентификатором причины.
3. Платёжный запрос не создаётся.

**A3. Повторный запрос с тем же идентификатором заказа**

1. Сервис обнаруживает ранее обработанный запрос с тем же ключом уникальности.
2. Сервис проверяет, допускается ли безопасный повтор запроса.
3. При совпадении параметров сервис возвращает ранее созданный результат либо его актуальное состояние.
4. При несовпадении параметров сервис возвращает конфликт.

Конкретный алгоритм повторной обработки фиксируется при проектировании API.

**A4. Торговая точка не имеет права принимать платежи**

1. Сервис отклоняет запрос.
2. Сервис возвращает соответствующую ошибку.
3. Платёжный запрос не создаётся.

### Результат

При успешном выполнении торговая точка получает данные QR-кода, связанные с конкретной покупкой. При ошибке возвращается результат, позволяющий определить причину отказа.

## 4. UC-02. Оплатить покупку по QR-коду

### Основная информация

| Параметр | Описание |
|---|---|
| Идентификатор | UC-02 |
| Цель | Позволить клиенту оплатить покупку по динамическому QR-коду |
| Основной актор | Клиент банка |
| Дополнительные участники | Мобильное приложение, сервис оплаты, внешняя платёжная инфраструктура |
| Предусловия | Клиент авторизован; платёжный запрос создан и не истёк; устройство подключено к интернету |
| Триггер | Клиент сканирует QR-код в мобильном приложении |

### Основной сценарий

1. Клиент открывает функцию сканирования QR-кода в мобильном приложении.
2. Приложение считывает QR-код и извлекает идентификатор платёжного запроса.
3. Приложение отправляет идентификатор в сервис оплаты.
4. Сервис находит платёжный запрос и проверяет его актуальность.
5. Сервис возвращает подтверждённые данные о покупке: получателя, сумму, валюту и описание.
6. Приложение отображает информацию о платеже.
7. Клиент проверяет данные и подтверждает оплату.
8. Приложение передаёт команду на подтверждение операции.
9. Сервис повторно проверяет возможность оплаты и применимые ограничения.
10. Сервис создаёт платёжную операцию с уникальным идентификатором.
11. Сервис передаёт запрос во внешнюю платёжную инфраструктуру.
12. Сервис получает окончательный результат либо фиксирует, что обработка продолжается.
13. Сервис сохраняет статус операции.
14. Приложение получает актуальный статус и отображает результат клиенту.
15. Сервис передаёт итоговый статус торговой точке по согласованному механизму.

### Альтернативные сценарии

**A1. QR-код не распознан**

1. Приложение не может извлечь корректный идентификатор.
2. Приложение сообщает клиенту, что QR-код не распознан.
3. Платёжная операция не создаётся.

**A2. Платёжный запрос не найден, истёк или уже использован**

1. Сервис обнаруживает, что запрос отсутствует или больше не доступен для оплаты.
2. Сервис возвращает соответствующий результат.
3. Приложение информирует клиента о невозможности выполнить оплату.
4. Новая платёжная операция не создаётся.

**A3. Клиент отменяет оплату**

1. Клиент закрывает экран оплаты или отказывается от подтверждения.
2. Приложение завершает сценарий.
3. Платёжная операция не создаётся.

**A4. Проверка ограничений не пройдена**

1. После подтверждения сервис выполняет необходимые проверки.
2. Одна или несколько проверок не пройдены.
3. Сервис не инициирует платёж либо возвращает отказ, если операция уже была передана на обработку.
4. Клиент получает допустимое для отображения сообщение о результате.

**A5. Внешняя платёжная инфраструктура возвращает отказ**

1. Сервис получает результат отказа.
2. Сервис сохраняет статус и доступную причину отказа.
3. Клиенту и торговой точке передаётся результат согласно согласованным правилам.

**A6. Истёк тайм-аут ожидания ответа**

1. Сервис не получил окончательный ответ в установленный срок.
2. Сервис не считает тайм-аут доказательством неуспешного платежа.
3. Сервис уточняет состояние уже созданной операции.
4. Клиент видит статус «В обработке», пока окончательный результат не установлен.

**A7. Повторное подтверждение**

1. Клиент или приложение повторно отправляет команду подтверждения.
2. Сервис проверяет идентификатор операции и ключ идемпотентности.
3. Повторный запрос не должен создавать вторую оплату той же покупки.
4. Сервис возвращает актуальный результат ранее инициированной операции.

### Постусловия

При успешном выполнении операция сохранена с успешным статусом, клиенту доступен результат, а торговая точка может получить подтверждение оплаты.

При отказе сохранён результат неуспешной операции.

При неопределённом результате сохранено состояние обработки, позволяющее продолжить получение статуса без дублирования платежа.

## 5. UC-03. Получить актуальный статус платежа

### Цель

Получить актуальное состояние ранее созданной платёжной операции.

### Основной сценарий

1. Клиент или система торговой точки запрашивает статус по идентификатору операции.
2. Сервис проверяет существование операции и права вызывающей стороны на получение соответствующих данных.
3. Сервис возвращает актуальный статус и доступные сведения об операции.
4. Если операция продолжает обрабатываться, возвращается промежуточный статус.

### Альтернативные сценарии

- Операция не найдена: сервис возвращает ошибку.
- Недостаточно прав: сервис отказывает в предоставлении данных.
- Статус временно недоступен: вызывающая сторона получает предусмотренную ошибку и может повторить запрос согласно правилам интеграции.

Детали запроса и ответа фиксируются в спецификации API.

## 6. UC-04. Передать результат платежа торговой точке

### Цель

Обеспечить получение торговой точкой актуального результата оплаты для обновления состояния заказа.

### Основной сценарий

1. Сервис фиксирует новый статус платёжной операции.
2. Сервис формирует уведомление, содержащее идентификатор заказа, идентификатор платёжной операции и итоговый статус.
3. Сервис отправляет уведомление по согласованному механизму интеграции.
4. Система торговой точки подтверждает получение уведомления, если это предусмотрено протоколом.
5. Сервис фиксирует результат доставки.

### Альтернативные сценарии

**A1. Ошибка доставки**

1. Сервис фиксирует неуспешную попытку доставки.
2. Повторная отправка выполняется по согласованной политике.
3. При необходимости торговая точка может запросить актуальный статус отдельно.

**A2. Повторное уведомление**

1. Торговая точка получает одно и то же уведомление повторно.
2. Торговая точка распознаёт повтор по идентификатору события или операции.
3. Повторная обработка не должна приводить к повторному зачислению платежа или дублированию заказа.

Детали гарантии доставки и обработки повторов должны быть согласованы при проектировании интеграции.

## 7. UC-05. Просмотреть информацию о выполненном платеже

### Цель

Предоставить клиенту возможность найти информацию о ранее выполненной операции.

### Основной сценарий

1. Клиент открывает историю платежей.
2. Приложение запрашивает доступные клиенту операции.
3. Сервис возвращает список операций в пределах разрешённого периода и доступного объёма данных.
4. Клиент открывает нужную операцию.
5. Приложение отображает сумму, получателя, дату и статус.

### Альтернативные сценарии

- Операций за запрошенный период нет: отображается пустой результат.
- Данные временно недоступны: приложение показывает сообщение об ошибке и предоставляет возможность повторить запрос.
- Операция продолжает обрабатываться: отображается актуальный промежуточный статус.
