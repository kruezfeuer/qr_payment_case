# Ошибки

## 1. Назначение документа

Документ описывает ошибки и коды отказа, которые возвращает сервис приёма платежей по QR-коду.

Цель документа — обеспечить единый формат обработки ошибок для торговой точки, банковского приложения и внешней платёжной инфраструктуры.

## 2. Общий формат ошибки

```json
{
  "error": {
    "code": "INVALID_REQUEST",
    "message": "Некорректные параметры запроса",
    "details": [
      {
        "field": "amount",
        "issue": "Сумма должна быть больше нуля"
      }
    ],
    "requestId": "2b7e2d74-2bd6-45d8-9a2f-8d3ec8b9e0a1",
    "timestamp": "2026-10-12T13:00:00Z"
  }
}
```

## 3. Принципы обработки ошибок

1. Ошибки должны быть структурированы и пригодны для автоматической обработки.
2. При наличии ошибок валидации сервис должен возвращать список проблемных полей.
3. Бизнес-ошибки должны отличаться от технических ошибок.
4. Повторные запросы при конфликтах идемпотентности должны возвращать понятный результат.
5. Ошибка доставки уведомления торговой точке не должна менять итоговый статус платежа.
6. Ошибка внешней платёжной инфраструктуры должна интерпретироваться отдельно от ошибки внутреннего сервиса.

## 4. Категории ошибок

| Категория | Описание |
|---|---|
| Ошибки валидации | Некорректный формат данных, отсутствие обязательных полей |
| Бизнес-ошибки | Запрос истёк, уже оплачен, превышен лимит, операция недоступна |
| Ошибки авторизации | Отсутствуют права доступа или недействителен токен |
| Ошибки идемпотентности | Повторный запрос с тем же ключом и другим содержимым |
| Технические ошибки | Внутренний сбой сервиса или внешней системы |
| Ошибки доставки | Не удалось доставить уведомление торговой точке |

## 5. Справочник ошибок по API

### 5.1. Создание платёжного запроса

| HTTP | code | Когда возникает | Что видит вызывающая сторона |
|---|---|---|---|
| 400 | `INVALID_REQUEST` | Не заполнено обязательное поле или неверный формат | Необходимо исправить запрос |
| 401 | `UNAUTHORIZED` | Нет авторизации | Доступ запрещён |
| 403 | `FORBIDDEN` | Торговая точка не имеет прав на создание запроса | Операция недоступна |
| 409 | `CONFLICT` | Повтор по тому же idempotency key с другим телом | Необходимо использовать корректный ключ |
| 422 | `UNPROCESSABLE_ENTITY` | Сумма, срок действия или параметры не соответствуют бизнес-правилам | Запрос не может быть выполнен |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка сервиса | Требуется повторить позже |

### 5.2. Получение данных платёжного запроса по QR

| HTTP | code | Когда возникает | Что видит клиент |
|---|---|---|---|
| 400 | `INVALID_REQUEST` | QR некорректен | QR нельзя использовать |
| 401 | `UNAUTHORIZED` | Клиент не авторизован | Требуется вход в приложение |
| 404 | `NOT_FOUND` | Запрос не найден | QR не распознан или запрос отсутствует |
| 410 | `GONE` | QR истёк или запрос недоступен | Оплата по этому QR больше невозможна |
| 422 | `UNPROCESSABLE_ENTITY` | Запрос нельзя использовать по бизнес-правилам | Оплата недоступна |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка | Повторите позже |

### 5.3. Подтверждение оплаты

| HTTP | code | Когда возникает | Что видит клиент |
|---|---|---|---|
| 400 | `INVALID_REQUEST` | Ошибка формата тела запроса | Необходимо исправить данные |
| 401 | `UNAUTHORIZED` | Нет авторизации | Требуется вход |
| 403 | `FORBIDDEN` | Клиент не может выполнять оплату | Операция запрещена |
| 404 | `NOT_FOUND` | Платёжный запрос не найден | Платёжный запрос недоступен |
| 409 | `CONFLICT` | Уже есть активная операция или повтор с другим содержимым | Операция уже обрабатывается |
| 410 | `GONE` | Запрос истёк или отменён | Оплата невозможна |
| 422 | `UNPROCESSABLE_ENTITY` | Нарушены бизнес-правила | Платёж не может быть выполнен |
| 503 | `SERVICE_UNAVAILABLE` | Внешняя платёжная инфраструктура недоступна | Повторите позже |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка | Повторите позже |

### 5.4. Получение статуса операции

| HTTP | code | Когда возникает |
|---|---|---|
| 401 | `UNAUTHORIZED` | Нет авторизации |
| 403 | `FORBIDDEN` | Недостаточно прав |
| 404 | `NOT_FOUND` | Операция не найдена |
| 500 | `INTERNAL_ERROR` | Внутренняя ошибка |

### 5.5. Уведомление торговой точки

| Ситуация | code / статус | Действие |
|---|---|---|
| Торговая точка вернула 2xx | `DELIVERED` | Зафиксировать успешную доставку |
| Торговая точка вернула 4xx | `FAILED` | Зафиксировать ошибку доставки, повтор может быть нецелесообразен |
| Торговая точка вернула 5xx | `RETRYING` / `FAILED` | Повторить доставку по политике повторов |
| Тайм-аут | `RETRYING` | Повторить доставку по установленному регламенту |

## 6. Бизнес-ошибки и причины

| Код причины | Ситуация | Комментарий |
|---|---|---|
| `PAYMENT_REQUEST_EXPIRED` | Срок действия запроса истёк | Новая оплата по запросу запрещена |
| `PAYMENT_REQUEST_PAID` | Запрос уже оплачен | Повторная успешная оплата невозможна |
| `PAYMENT_REQUEST_CANCELED` | Запрос отменён | Оплата невозможна |
| `DUPLICATE_OPERATION` | Попытка создать дублирующую операцию | Нужно использовать текущую операцию |
| `LIMIT_EXCEEDED` | Превышен лимит суммы или количества операций | Требуется корректировка параметров |
| `MERCHANT_NOT_ACTIVE` | Торговая точка неактивна | Запросы не принимаются |
| `PROVIDER_REJECTED` | Внешняя система отклонила платёж | Возврат окончательного отказа |
| `PROVIDER_TIMEOUT` | Итог по операции не получен вовремя | Результат уточняется позже |
| `NOTIFICATION_DELIVERY_FAILED` | Уведомление торговой точке не доставлено | Не меняет статус платежа |

## 7. Правила логирования ошибок

1. В логах должен сохраняться `requestId` или иной идентификатор корреляции.
2. В логах не должны сохраняться секреты авторизации.
3. Для бизнес-ошибок должны быть доступны код причины и текст, пригодный для диагностики.
4. Для технических ошибок должны быть доступны сведения, достаточные для расследования инцидента.
5. Ошибки доставки уведомлений должны фиксироваться отдельно от статуса платежа.
